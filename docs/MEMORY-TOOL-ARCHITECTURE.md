# 记忆工具 · 架构设计与可行性分析

> 架构师：高见远 ｜ 日期：2026-11-08

> 范围声明：本阶段**只出分析与设计，不写实现代码**。

## 0. 一句话结论

**做成 Prompt Scaffold 的"记忆系统"扩展模块，而非独立新产品；分三步走——先本机零成本把"记、找、版本、备份"做扎实，再把"AI 总结 + 本地提醒"补上，最后才评估要不要上云端同步。**

## A. 定位判断（重要，先回答）

### 结论：作为 Prompt Scaffold 的**扩展模块**（把现有"轻量记忆层"升级为完整记忆系统），**不做独立新产品**。

### 理由

1. **记忆本就是既有路线，不是新方向。** PRD-v5 §三·第三层已明确"用户自定义记忆仓库"是三层知识底座的一层；代码里已有 `MemoryHabit / dimensionHabits`、`src/shared/memory.ts`、记忆库导入导出（ARCHITECTURE-v2 问题2）。用户提的 10 条，是把"轻量记忆层"升级为"完整记忆系统"，是**同一条线的加深，不是另起炉灶**。

2. **使用场景与 Scaffold 强绑定。** 用户要记的东西是"维度措辞习惯、已确认的需求底稿、跨任务偏好"——这些内容**只有 Prompt Scaffold 会产生和使用**。独立新产品没法自动得到这些素材，反而要重新获客、重新搭窗口/托盘/模型/存储全套基建，成本翻倍、价值减半。

3. **基建可 100% 复用。** 现有 Electron 窗口、托盘、`store.ts` 原子写存储、`llm.ts` 模型接入、i18n、导入导出、测试框架，全部直接复用。扩展模块的新增成本主要集中在"数据模型 + 存储层 + 若干面板"。

4. **边界要划清楚（关键取舍）。** 10 条里，第 7 条「跨设备同步」和第 2 条「跨设备推送」**超出了"本地桌面工具"的能力边界**（需要云端后端 + 账号体系）。这两条**不应一开始就承诺**，而是作为 P2 的可选方向单独立项评估——**不因它们的存在而把整个记忆工具判成"独立产品"**。

### 定位表述（给产品的一句话）

> Prompt Scaffold 由「维度清单 + 对话总结 + 需求底稿 + 记忆层」组成；本次是把"记忆层"从"只记偏好"升级为"记忆系统"：**记、找、版本、备份、本地总结提醒**都在本机完成，**同步**作为后期可选能力，遵循"先本地后云端、先易后难"。

## B. 逐条可行性 + 利弊分析（核心）

> 难度口径：容易=本机零/低成本、复用现有能力；中等=本机可做但有工程量；难/有风险=需要云端后端或引入新依赖，需慎重。

### 第 1 条：记忆工具功能（记录一天/一周/一月时段的记忆内容）

- **可行性**：✅ 容易。核心是"时间桶聚合"——记录时打时间戳，展示时按 天/周/月 聚合，纯本地 JSON 即可。
- **利（价值）**：这是整个模块的基座；"分时段"本质是**时间维度上的索引**，让记忆可回看、可追踪。
- **弊（成本/风险）**：注意别过度设计成"日历/日记 App"。时段应是**派生视图**（由 `createdAt` 计算），而不是独立实体，否则会引入"一条记忆属于多个桶"的同步难题。
- **关键取舍**：**时段 = 聚合视图，不是存储实体**；保留策略（天/周/月各保留多久）做成配置项。

### 第 2 条：总结与提醒（自动总结可能忘记的内容 + 提醒）⚠️ 高风险点

- **可行性**：**中等（分两半看）**。①"自动总结"= 复用现有 `llm.ts` 做一次 LLM 调用，**容易**；②"提醒"= Electron 托盘通知 + 本地定时调度，**中等的工程成本**。
- **利**：总结 + 提醒是"记忆"产生价值的临门一脚——只记不看等于没记，提醒让工具从"被动仓库"变"主动助手"。
- **弊（成本/坑）**：
  - **AI 总结把用户记忆发给第三方模型**，与"隐私优先"冲突，必须**默认关闭 + 明示数据流向 + 用户可切本地模型**（PRD 已规划 SmolStruct 类本地模型兜底）。
  - **本地提醒不可靠**：托盘通知在应用运行时才有效，**关机/退出后错过**；真"后台推送"需要云端服务（见第 7 条），成本陡增。
  - 定时任务在主进程用 `setInterval`/`node-cron` 类调度，须遵守我们已有的铁律：**定时器回调内禁止裸抛**（ARCHITECTURE-v2 §10.1），否则复现"闪退"。
- **关键取舍**：**MVP 只做"应用运行时的本地托盘提醒"**（`Electron Notification` + `Tray`），明确告知"退出后不提醒"；跨设备/离线推送推迟到 P2 与同步一起决策。
- **推荐落地**：主进程 `ReminderScheduler` 每分钟扫一次到期提醒 → `new Notification()` 弹托盘通知；"总结"由用户点按钮触发（手动），先不做后台自动总结，避免隐私争议。

### 第 3 条：数据保存周期（一天/一周/一月的保存）

- **可行性**：✅ 容易。就是一个**保留/归档策略**：每条记忆带时段归属，按周期配置"保留最近 N 天/周/月"，过期归档或软删。
- **利**：控制数据增长、聚焦近期记忆，符合"人更容易忘记近期的细碎"。
- **弊**：自动删除用户数据有风险（用户以为"永久"），必须**软删除 + 回收站 + 可恢复**，绝不物理删除。
- **关键取舍**：保留策略默认"永不自动删除，仅归档折叠"；若提供自动清理，必须是**用户显式开启**的选项。

### 第 4 条：资料仓库（历史版本资料的保存仓库）

- **可行性**：✅ 中等。文件 + 元数据管理，本地目录 + JSON 索引即可。
- **利**：把"记忆"（碎片）和"资料"（文档/文件）统一收纳，是任务二的另一块核心资产。
- **弊**：文件管理有坑——**文件路径、二进制、重命名、外部被删**都要处理；不要试图做"文件同步盘"（那是 Dropbox 的地盘）。
- **关键取舍**：**资料仓库 = 元数据索引 + 本地文件引用**，不复制、不监控、不同步系统文件；文件本体用 `copyTo` 纳入仓库目录（内聚、可整体备份），而非引用散落路径。

### 第 5 条：版本控制（历史版本保存，防误删/丢失）⚠️ 设计重点

- **可行性**：**中等偏易（设计选型是关键）**。
- **利**：防误删、可回滚，直接解决"改坏了找不回"的高频痛点。
- **弊（成本/坑）**：版本存储有两条路线，**选错会变复杂**：
  - **快照（snapshot）**：每次保存存**完整副本**，append-only 不可变，实现最简单、最可靠、可回滚。
  - **diff（差异）**：只存变化量，省空间但实现复杂、合并易错、损坏时整链不可读。
- **关键取舍 + 推荐**：**记忆/资料都是小文本量，用"append-only 快照 + 软删除 + 保留最近 N 版/最近 M 天"**。不要上 diff/git 级复杂度。每条实体：`id` 不变，每次修改新增一条 `version` 记录（`versionNo / content / checksum / createdAt / note`），`currentVersion` 指向最新；删除只打 tombstone。数据量到万级再考虑压缩（只保留每版 diff 之前的全文，或定期 compact）。

### 第 6 条：用户界面（直观易用）

- **可行性**：✅ 容易。复用现有 React 18 + Tailwind + 现有弹窗/列表样式（`MemoryLibrary.tsx` 已是现成范例）。
- **利**：低门槛是"用得起来"的前提。
- **弊**：功能一多 UI 会乱（记/找/资料/版本/备份五个入口）。
- **关键取舍**：**统一入口 = 一个"记忆"面板 + 顶部 Tab（记忆 / 资料 / 回收站 / 备份）**，搜索框全局置顶，别做成五个散落按钮。

### 第 7 条：数据同步（跨设备）⚠️⚠️ 最高风险/成本点

- **可行性**：**难 / 有风险**。需要云端后端 + 账号体系，与现有"本地存储、隐私优先、无需账号"的既定路线**正面冲突**。
- **利**：多设备一致性是真实价值，尤其"公司+家里""电脑+手机"场景。
- **弊（成本/风险/坑）**：
  1. 引入账号、服务器、运维、合规（个保法 PIPL、数据跨境）一整条链，**成本从"零"跳到"持续投入"**。
  2. 破坏"无需账号、数据不出机"的信任卖点——**这是本项目目前最重要的差异化之一**。
  3. 同步冲突（多端并发改同一记忆）是经典难题，做浅了丢数据、做深了要做 CRDT/OT。
- **三个可选方案权衡**：

| 方案 | 成本 | 隐私 | 冲突处理 | 结论 |
|---|---|---|---|---|
| A. **纯本地导出/导入**（现有能力，跨设备靠文件+U盘/网盘手动搬） | 零 | 最好 | 人工（导入时 merge/overwrite） | ✅ **推荐先做**，P0/P1 |
| B. **端到端加密云同步**（自建后端 + 账号 + 客户端加密后上传） | 高（后端+运维） | 好（服务端只见密文） | 需设计 | P2 再评估，仅当用户真实付费需求被验证 |
| C. **第三方存储接入**（WebDAV / S3 兼容 / 网盘，同步一个加密容器文件） | 中（无自建后端，但依赖第三方） | 好（端到端加密文件） | 弱（整文件级，最后写入胜） | 介于 AB 之间，作为 P2 的轻量折中 |

- **关键取舍 + 推荐**：**A 先行，把"导出/导入 + 合并冲突校验"打磨好（已有基础）；B/C 作为 P2 可选方向，且必须先做端到端加密，绝不裸传。** 本轮**不立项云端**。

### 第 8 条：搜索与检索 ⚠️ 选型重点

- **可行性**：**中等**。小数据量纯 JS 全文检索够用；向量检索是"数据量大 + 语义模糊回忆"时才需要的重武器。
- **利**：搜索是记忆系统的价值兑现点（"我上次那个关于 XX 的东西"）。
- **弊（成本/坑）**：**本项目的硬约束决定了 SQLite 并不顺**：
  - `node:sqlite` 需要 Node ≥22.5，**Electron 34 内置 Node 20.18，用不了**；
  - `better-sqlite3` 是 native 模块，需要 node-gyp + MSVC 工具链，**本机 Rust/MSVC 工具链缺失**（PRD-v5 §八已记录）；
  - `sql.js`（WASM）纯 JS 但**无 FTS5**，且是内存库要手动持久化。
- **关键取舍 + 推荐**：
  - **P0/P1：继续 JSON 存储（源事实）+ 纯 JS 全文索引 `MiniSearch`（或 `FlexSearch`）**，支持前缀 + 模糊（编辑距离）+ 字段权重，完全够用，零 native 依赖。
  - **什么时候值得上向量库**：数据量到 **十万级条目**、且用户明确需要**语义模糊回忆**（同义改写、跨语言、'记不清原话'）、并**愿意为 embedding 付费/接受调用云端 embedding** 时。**在此之前，MiniSearch + 标签粗筛（PRD 的"标签粗筛→关键词精排"两段式）已覆盖 95% 场景。** 结论：**本轮不上向量库**。

### 第 9 条：数据备份与恢复 ⚠️ 设计重点

- **可行性**：**中等**。本地自动备份 + 手动恢复，零云端成本。
- **利**：是防丢失的最终兜底，比版本控制更"保命"。
- **弊（成本/坑）**：备份要防"备份自己损坏"和"覆盖好备份"；云端备份又回到第 7 条的隐私/成本问题。
- **关键取舍 + 推荐**：
  - **本地自动备份**：定期（如每日首次启动 + 退出前）把整个数据目录打包为带时间戳的 `backup-YYYYMMDD-HHmmss.zip/json` 存到用户指定备份目录，**保留最近 N 份轮转**，不覆盖；
  - **恢复**：从备份文件导入（复用现有导入/校验/合并能力）；
  - **存储策略**：数据目录内"源数据 + 版本 + 备份清单"三区分离，备份区独立于源数据区，避免一损俱损；
  - 云端备份 → 归入第 7 条同步一起决策（P2），不单独开。

### 第 10 条：隐私保护

- **可行性**：**中等偏易**（本机默认天然满足；风险来自第 2 条 AI 总结与第 7 条同步这两个"出机"动作）。
- **利**：隐私是本项目立身之本，守住它 = 守住差异化。
- **弊**：加密（本地静态加密）会引入密钥管理复杂度；"过度保护"（如强加密）会拖慢开发、增加找回成本。
- **关键取舍 + 推荐**：
  - **默认：数据全部本地、不出机、不采集、不埋点**（延续现状）。
  - **本地静态加密（可选，P1 后期）**：数据目录加 `electron-safeStorage`（OS 级密钥）或用户口令派生密钥加密，作为可选项而非默认（避免用户忘密钥丢数据）。
  - 任何"出机"动作（AI 总结 / 同步）**必须显式告知数据流向 + 默认关闭 + 一键关闭**。

## C. 架构设计（可落地版本）

### C.1 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 形态 | **延续 Electron 桌面版**（Electron 34 + electron-vite + React 18 + TS + Tailwind） | 复用全部现有基建，零新依赖，符合本机无 Rust/MSVC 的约束 |
| 数据层 | **继续 JSON 文件 + 原子写**（多文件分域：memory / materials / versions），**不引入 SQLite** | 见 §B-8 的 Node 版本与工具链约束；延续 `store.ts` 的"tmp 原子写 + 降级"模式 |
| 搜索 | **MiniSearch**（纯 JS FTS，前缀+模糊+字段权重） | 零 native 依赖，小数据量最顺 |
| AI 总结 | **复用现有 `llm.ts`**（OpenAI 兼容 + 用户自备 key），默认关闭，可切本地模型 | 延续"模型是增强项，不接也能跑" |
| 提醒 | **Electron `Notification` + `Tray` + 主进程调度器** | 本机零成本；不引入云端推送 |
| 备份 | 本地 zip/JSON 快照轮转 | 零云端成本，隐私友好 |
| 同步 | **P2 才评估**：端到端加密云同步 or WebDAV/S3 第三方 | 本轮不做后端 |
| 加密 | （可选）`electron safeStorage` | 需要时再加，不作默认 |

### C.2 数据模型（实体 + JSON schema）

> 存储落地为数据目录下的多文件 JSON（沿用现有 `store.ts` 原子写模式）。以下为**逻辑模型**；物理上 `memory.json / materials.json / versions.json / backup-manifest.json` 分文件，避免单文件过大。

```
MemoryEntry 记忆条目
  id: string (uuid)
  content: string            // 记忆正文
  kind: 'note'|'todo'|'insight'|'habit'|'draft-constraint'   // 类型；habit/draft 与现有维度习惯、需求底稿打通
  tags: string[]
  period: 'day'|'week'|'month'        // 派生字段，由 createdAt 计算，展示用
  source: 'manual'|'ai-adopted'|'imported'
  pinned: boolean
  archived: boolean          // 软删除用（进回收站）
  createdAt: string          // ISO 8601 UTC
  updatedAt: string

MaterialDoc 资料仓库条目
  id: string
  title: string
  fileRef: string            // 仓库目录内文件路径（copyTo 内聚）
  contentType: string        // text/markdown/pdf/...
  checksum: string
  tags: string[]
  currentVersionId: string
  createdAt / updatedAt: string

DocVersion 资料版本（append-only）
  id: string
  docId: string
  versionNo: number
  fileRef / content: string  // 完整快照
  checksum: string
  note: string               // "改了标题"
  createdAt: string

ReminderTask 提醒任务
  id: string
  targetId: string           // 指向 MemoryEntry / MaterialDoc
  remindAt: string           // ISO 8601 UTC
  repeat: 'none'|'daily'|'weekly'
  status: 'pending'|'fired'|'dismissed'
  channel: 'tray'            // MVP 仅托盘

BackupManifest 备份清单
  id: string
  path: string
  createdAt: string
  scope: 'full'              // MVP 全量
  checksum: string
```

**版本控制 schema（第 5 条落地）**：`DocVersion` 采用 **append-only 完整快照**；`MaterialDoc.currentVersionId` 指向最新；删除打 tombstone（`archived: true`），保留最近 N 版、N 可配置。

```mermaid
    MAS -->|删除| RB[RecycleBin 软删除]

    MS --> SI[search-index.ts MiniSearch]
    MAS --> SI
    SB --> SI

    MS --> RS[reminder-scheduler.ts]
    RS -->|到期| NT[Electron Notification 托盘通知]

    MS --> BM[backup-manager.ts]
    MAS --> BM
    BM -->|每日/退出前| BZ[backup-*.json 轮转]

    MP -->|点总结(可选,默认关)| SUM[summarize.ts]
    SUM -->|调用户模型 key| LLM[llm.ts]
    LLM -->|明文记忆需用户授权| API[第三方 LLM API]
```

### C.5 分阶段路线（先易后难、先本地后云端）

| 阶段 | 内容 | 云端/后端 | 新增依赖 | 说明 |
|---|---|---|---|---|
| **P0（本机零成本，先做）** | 记忆条目 CRUD + 天/周/月时段聚合视图 + 资料仓库 + **版本快照** + **MiniSearch 搜索** + 回收站软删除 + 导出/导入 + 手动备份 | 无 | `minisearch`（纯 JS） | 全是复用现有 JSON 存储 + React 的能力，零云端、零 native |
| **P1（本机 + 轻度 AI）** | 本地托盘提醒（应用运行时）+ **手动触发的 AI 总结**（默认关、可切本地模型）+ 自动定期本地备份轮转 + （可选）本地静态加密 | 无 | `electron-safeStorage`（内置） | AI 总结复用 `llm.ts`；提醒不承诺退出后送达 |
| **P2（云端/后端投入，需再立项）** | 跨设备同步（端到端加密）或 WebDAV/S3 第三方同步 + 云端备份 + 语义向量检索 | **需要**（账号/后端 or 第三方） | embedding + 后端 | 仅当用户真实付费需求被验证后才做；先端到端加密 |

## D. 风险与合规

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **第 7 条同步破坏"本地优先、无需账号"信任** | 产品差异化丢失、用户流失 | 同步作为 P2 可选项，默认本地；必须端到端加密，绝不裸传；A 方案（导出导入）先满足迁移诉求 |
| 2 | **第 2 条 AI 总结把用户记忆发给第三方** | 隐私泄露、信任受损 | 默认关闭 + 明示数据流向 + 支持切本地模型（SmolStruct 类）+ 一键关闭 |
| 3 | **第 2 条提醒"退出后不送达"被误解** | 用户预期落差 | 明示"应用运行时提醒"；跨设备/离线推送归入 P2 |
| 4 | **数据丢失（写坏/误删/备份损坏）** | 不可逆 | 沿用"tmp 原子写 + 降级 + 重试"；版本快照 + 软删除 + 备份轮转；退出前 flush |
| 5 | **自动删除/清理误伤数据** | 不可逆 | 保留策略默认"永不删，仅归档"；清理须用户显式开启 + 回收站 |
| 6 | **定时器回调裸抛（历史教训）** | 复现"闪退" | 提醒调度器遵守 ARCHITECTURE-v2 §10.1：定时器回调内全 try-catch，主进程已有 uncaughtException 兜底 |
| 7 | **SQLite/native 依赖破坏"零 native"约束** | 本机无法编译 | 坚持 JSON + MiniSearch；确需 SQLite 时等 Electron 升 Node 或工具链就绪后再评估 |
| 8 | **法规/合规** | 合规风险 | 见下方专项说明 |

### 合规专项说明

1. **个人信息保护（中国 PIPL）**：记忆内容极可能含个人信息/敏感信息。**默认本地存储不构成"处理"的对外传输**；一旦做同步（第 7 条）或 AI 总结（第 2 条）上传，即涉及"对外提供/委托处理"，需**用户知情同意 + 最小化 + 可删除 + 数据出境评估**（用海外 LLM API 时）。
2. **数据最小化与可删除**：提供"一键导出 + 彻底删除"，删除要真删（含备份、版本、索引），满足"被遗忘权"。
3. **加密**：同步（P2）必须端到端加密（服务端只存密文）；本地静态加密作为可选。
4. **不采集、不埋点**：延续现状，不做行为分析，从源头降低合规面。
5. **敏感行业提醒**：若用户拿它记医疗/金融/法律内容，须提示"本地工具不构成合规存储方案"，避免工具被误当合规系统使用。
