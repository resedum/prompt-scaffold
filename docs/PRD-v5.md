# 需求底稿（Prompt Scaffold）· 最终计划书 v5

> 本版融合「项目定位讨论结果」与「PRD v4 形态决策 + 架构师可行性结论」，补齐此前丢失的核心思想，删除冗余的版本变更记录与重复线框。本文档是项目的权威定义。

---

## 一、项目定位（为什么做）

起点很小：一个帮用户优化提示词的插件。但几轮讨论后核心问题被重新定位——**用户说不清，往往不是"话说得不够好"，而是"一时想不到该说什么"**。

三个更隐蔽的痛点：

1. AI 追问发生在它开始思考之后；长周期任务里缺陷暴露得晚，返工代价复利式增长。
2. 长对话中 AI 的上下文压缩会**静默丢掉用户约束**。
3. 用户自己也会逐渐忘记最初要什么——**双方手里都没有一份可信的、不变的参照物**。

所以本项目只做一件事：**在用户开口前帮他把需求想全，在长对话中帮他把要求守住**。它不替用户写提示词，它产出**可勾选、可修改的原材料**。

> 一句话收束：押注的不是"提示词工程"这个可能被模型进化吃掉的市场，而是"人需要外部认知支架，把没说出口的要求摆到眼前，并在长任务中守住它们"这个更长期的问题。

## 二、它是什么：三块能力

### 能力一：输入前的维度清单与具体建议

用户写下一句模糊指令后，工具给出一组"你可能漏掉的维度"，**每条后面跟一句可直接采用或修改的具体措辞**，而不是只丢一个词让用户自己想。

- 例：「行距 → 建议正文 1.5 倍行距」「表格 → 建议居中、表头加粗、边框细线」。
- 用户勾选、删改、拼接，最终产物是**"用户自己的输入 + 一段补充说明"**，不是被 AI 改写过的提示词。
- **勾选权和取舍权始终在用户手里。**

### 能力二：长对话中的需求底稿

工具扫描用户**自己发出的消息**，提取当前仍有效的目标、硬约束、已修正项、已撤回项，生成一份用户可逐条确认的底稿：「仍然要 / 不要了 / 改一下」。

- 确认后的版本保存在本地，用户随时可调出对照，也可选择**重新注入对话**作为提醒。
- 它不替代 AI 内部的上下文压缩；它服务的是**用户对"我到底要什么"的最终解释权**。
- 与"对话总结"的关系：对话总结是"一次性输入一段对话 → 提炼核心诉求"；需求底稿是"长期追踪自己发的消息 → 维护一份活的、可确认的约束清单"。二者并存，底稿是守住要求的核心机制。

### 能力三：有知识底座和记忆层支撑，不是模型凭空发挥

维度清单和具体措辞**优先从公共提示词仓库检索、拆解、映射**，再用框架库做补全检查；用户长期偏好存于可写的个人记忆仓库，生成时自动召回。**模型负责筛选和润色，不负责发明维度。**

---

## 三、知识底座：三层架构

### 第一层：公共知识库（只读）

GitHub 上的提示词仓库（如 PGP、prompt-optimizer-skill 的框架文件），或通过现成 MCP 提示词服务器接入。工具只做**检索、拆解、映射**，不向公共库写入。拆解产物是「维度词」和「具体表述」两类字段，**每条保留来源标记**。

### 第二层：标签化索引层（工具治理）

公共库和个人库遵循同一套元数据契约，预置标签维度：

- **Category**：writing / coding / research / data / marketing / operations / creative
- **Output format**：json / markdown / bullet-list / prose / code / table
- **Status**：draft / reviewed / deprecated
- **Source**：public / user / framework

用户可增加自定义标签，但与预置维度分开存储。检索两段式：**先按标签做确定性粗筛，再在粗筛结果上做关键词或语义精排**；第一版用 SQLite FTS 即可，不引入向量数据库。

### 第三层：用户自定义记忆仓库（可写，写入权在用户）

本地 Markdown / YAML 文件，用户可直接编辑或通过面板编辑。核心原则：**AI 只能提议，不能决定**——AI 提出的记忆条目进入"待确认"区，用户点"采纳"才写入；没有自动采集、自动总结、后台回写。

内容范围是跨任务可复用的偏好和规则，如「文档永远要求宋体小四、1.5 倍行距」「报告一律需要页码和图表题注」。它与需求底稿打通：**底稿确认后，用户可把其中"以后也适用"的条目提升为长期规则**，下次生成清单时自动召回。

---

## 四、交互原则（四条铁律）

1. **不替用户做决定** —— 产出可勾选、可逐条修改的原材料，不是最终答案。
2. **不编造** —— 用户没提供的信息写成「待补」占位，不替用户填空。
3. **不静默改写** —— 用户原话不被覆盖，补充说明以追加形式存在；已撤回项**保留标记而非删除**。
4. **知道什么时候闭嘴** —— 连续多次忽略提醒后自动进入静默期。

## 五、产品形态与接入

- **第一版**：本地运行的**轻量桌面软件（独立小窗，Windows 首版）**，读输入、展示清单、生成补充说明、保存底稿，**不做云端上传**。
- **输入**：文字 / 图片（内置一键截图 + 粘贴剪贴板 + 拖入文件）/ 多轮对话文本。
- **输出**：维度清单、需求底稿、对话总结，分别可复制，也可一键复制合并。
- **接入路线**：深度体验优先以**钩子形式接入一个常用 Agent**（占据"按下发送键之前"的必经位置）；**MCP Server** 作为广度补充；跨 Agent 覆盖按适配器逐个扩展，第一版不追求数量。

## 七、模型策略（功能分工 + 用户自选）

**按功能分工，不整体切换**，同时保留"用户自选"的形态（base_url / api_key / model 可改）：

| 场景 | 模型 | 说明 |
|---|---|---|
| 主力（维度建议 / 措辞润色 / 底稿提取） | DeepSeek V4-Pro 类（默认，用户可改） | 成本低，适合反复调 prompt |
| 超长粘贴分流 | Qwen-Long 类（长上下文） | 超长对话文本的提取 |
| 隐私硬约束 | SmolStruct-1.7B / Schemer 类（本地） | 数据不出机的本地底稿提取 |

**关键前提**：第一阶段不接任何模型也能跑通——**规则 + 硬编码维度池是前置基础，模型是增强项**。这降低冷启动门槛，也保证"无 key / 断网"时工具仍可用（明确标注"未使用 AI，仅框架提示"，不冒充 AI 生成）。

## 八、技术方案与可行性（架构师结论）

**本机实测**：Node v22.22.2 ✅ / npm 10.9.7 ✅ / 网络可达 ✅ / **Rust + MSVC 构建工具链缺失 ❌** / 无包管理器 ❌ / Windows 11 x64。

| 技术点 | 结论 | 方案 |
|---|---|---|
| 桌面框架 | **Electron（推荐）**；Tauri 本机不可行 | Electron ^34 零 native 依赖；Tauri 需先装 6–8GB 工具链 |
| 多模态识图 | 可行 | OpenAI 兼容 `image_url` base64，provider 归一化兜底厂商差异 |
| 内置截图 | 可行 | `desktopCapturer` + 自绘选区，纯 JS |
| 剪贴板/拖拽 | 可行 | `clipboard.readImage()` + HTML5 DnD |
| 本地存储 | 可行 | JSON 文件 + 原子写（不用 SQLite，避开 native 编译） |
| 长对话处理 | 可行 | 截断 / 分段总结 / 硬上限提示 |
| 托盘常驻 | 可行 | Electron `Tray` |

**整体判断：可行，无阻断性风险，零原生编译依赖。**

技术栈：Electron + electron-vite + electron-builder · React 18 + TS + Tailwind · openai SDK · JSON 存储 · Electron 内置 API（截图/剪贴板/托盘）。

> 权衡：Electron 体积大（包 ~150MB / 运行 ~300MB），但本机免装环境、开发快；前端代码后续可复用迁移 Tauri（需先补 Rust 工具链）。

## 九、分阶段实现路线图

- **阶段一（首版）**：输入前澄清 —— 独立小窗 + 文字/图片输入 + 维度清单 + 模型接入（API）+ 记忆偏好 + 内置截图/托盘 + 对话总结。**规则 + 硬编码维度池兜底，不接模型也能跑。**
- **阶段 1.5**：接入公共知识库 —— 种子仓库 + 本地索引 + 检索函数。
- **阶段 1.6**：标签化索引层 + 用户记忆仓库 —— 实现"AI 提议 / 用户采纳"流程和"底稿提升为长期规则"的衔接。
- **阶段二**：需求底稿 —— 与记忆仓库共用本地存储和确认交互。
- **阶段三**：接入一个 Agent 的钩子 —— 把手动粘贴换成自动读取，把复制换成插入输入框。
- **阶段四**：视前三阶段实际使用情况，再决定 MCP Server 和多 Agent 适配。

## 十、它不做什么（边界）

1. 不做一键生成"完美提示词"。
2. 不做自动改写替换（用户原话不被覆盖）。
3. 不逆向、不注入任何 Agent 本体。
4. 不第一版就铺开跨所有 Agent 的适配矩阵。
5. 不把公共仓库内容直接喂给用户而不做场景过滤和粒度转换。

---

## 十一、怎么判断它值得继续做（评测）

用同一个真实的长周期任务跑两组：

- **A 组**：直接开跑。
- **B 组**：先用本工具澄清并保存底稿。

中途和结尾各对照一次，记录两组分别在**第几步开始偏离用户要求、最终返工量差多少**。

- 若 B 组没有明显优势 → 回头检查**维度筛选规则、知识底座检索质量、底稿归类逻辑**，而不是加更多功能。

---

## 十二、风险点

1. Electron 体积/内存较大 —— 首版接受，可迁移 Tauri。
2. 视觉模型厂商字段差异 —— provider 归一化兜底。
3. 结构化 JSON 偶发不稳定 —— JSON mode + 容错解析 + 重试/退化两次调用。
4. 长对话超上下文 —— 三段式降级。
5. 截图多显示器/DPI 偏移 —— 按 display 源 + scaleFactor 校准，首版主屏优先。
6. 记忆治理 —— 同维度冲突默认提示选择、与公共库冲突提示过时、"永远"类必设复审期。
