## 2. 产品定义

### 2.1 产品目标（一句话）

一个**独立打开的桌面小窗软件**：用户输入文字、**粘贴/拖入截图**、或**粘贴一段多轮对话**，软件通过**调用用户自选的大模型 API** 先总结/理解诉求，再自动补全漏掉的维度清单（每条带可采纳措辞），用户勾选/编辑后生成补全后的完整指令，**一键复制**到任意 AI 输入框——不依赖任何宿主，随开随用。

### 2.2 三个核心目标（正交）

1. **形态目标**：独立桌面小窗软件，可脱离宿主浮在桌面、随开随用、不占对话空间。
2. **智能目标**：**维度清单 + 对话总结**均由**用户自选的真实大模型 API** 生成（文字走文本模型，图片走多模态视觉模型），主路径零硬编码规则；结构化输出稳定解析。
3. **交互目标**：在窗口内一次完成"输入（文字/图片/对话）→ 生成 → 勾选/编辑 → 采纳 → 复制"闭环，用户始终握有取舍权。

### 2.3 用户故事

- **故事 A（打开软件）**：作为用户，我想快速打开一个独立小窗（双击图标/托盘唤起），把一句模糊指令（如"帮我写一份报告"）打进去或粘贴进去，即可开始澄清，无需依赖任何对话宿主。
- **故事 B（截图识图）**：作为用户，我看到一份需求文档/一张设计稿截图，我把截图**粘贴到软件里、拖入图片文件或一键截图**，软件能识别图中内容，并把它当作澄清对象，帮我补全图中未说清的要求。
- **故事 C（生成维度）**：作为用户，我在窗口里看到大模型为我补全的维度清单（目标读者、篇幅、语气、格式……），每条带一句可直接采用或修改的措辞，不必自己凭空想。
- **故事 D（勾选/编辑/复制）**：作为用户，我勾选、编辑、删除、增补维度后点"生成完整指令"，得到"原始输入 + 补充说明"，一键复制到剪贴板，粘贴到任意 AI 输入框即可获得更高质量输出。
- **故事 E（自选模型 / 失败降级）**：作为用户，我用自己选的大模型、自己填的 key 来跑；当没配置或请求失败时，软件给出明确提示与可操作的修复路径（去配置 / 重试 / 换一个模型），而不是退回冷冰冰的写死清单。
- **故事 F（越用越懂我）**：作为用户，我希望软件记住我常用的模型、语言、界面和维度措辞习惯，下次自动还原、优先命中，让我更快确认。
- **故事 G（对话总结）**：作为用户，我把一段多轮对话记录粘贴/拖入软件，软件先总结出这段对话的**核心诉求与结论**，再基于总结补全维度清单，我分别复制"总结"或"补全后的指令"继续后续工作。

## 5. AI 接入方案

**协议：OpenAI 兼容协议**，用户自填 `base_url + api_key + model` 三字段（云端/本地/聚合平台通用）。

**模型选择权在用户**，不固定默认模型；软件提供**预设**只用于"一键填好 base_url 和 model 建议值"，key 始终由用户自己填：

| 预设 | base_url 建议 | model 建议 | 说明 |
|---|---|---|---|
| 智谱 | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash`（文本）/ `glm-4v-flash`（视觉） | 免费文本档 |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` | 便宜、质量好 |
| Ollama（本地） | `http://localhost:11434/v1` | 用户本地模型名 | 数据不出机 |
| 自定义 | 用户任意填 | 用户任意填 | 完全自由 |

**结构化输出（维度清单）**：要求模型返回严格 JSON，前端容错解析（剥离 markdown 代码块）：

```json
{
  "dimensions": [
    { "name": "目标读者", "wording": "面向公司管理层" },
    { "name": "篇幅",     "wording": "正文 3000 字左右" }
  ]
}
```

**结构化输出（对话总结，两段合一）**：对话总结模式用一次调用同时返回总结 + 维度，简化延迟与成本：

```json
{
  "summary": {
    "goal": "核心诉求",
    "conclusions": ["已确认结论 1", "已确认结论 2"],
    "constraints": ["硬约束 1"],
    "open": ["悬而未决 1"]
  },
  "dimensions": [
    { "name": "目标读者", "wording": "…" }
  ]
}
```

> 若一次调用不稳定，可退化为两次调用（先总结、再补全维度），作为实现侧的可选策略。

**视觉模型接入（截图识图场景）**：

- 当输入含图片时，改走**多模态视觉模型**（同一 OpenAI 兼容协议，仅 `model` 字段换成支持视觉的模型，如 `glm-4v-flash`、`qwen-vl` 系列等），把图片 + 用户文字一起作为输入，先"识别/理解图中内容"，再据此补全维度。
- 若用户所配模型不支持视觉（API 返回不支持图片输入）→ 明确报错"当前模型不支持图片识别，请换一个视觉模型"，并给出切换引导。
- **可选降级**：图片→文字 OCR（本地或轻量 OCR），把识别文字作为文本喂给文本模型；作为"视觉模型不可用"时的兜底（P1）。

**降级策略（降级也要"可用"，绝不退回纯硬编码冒充主路径）**：

1. **未配置 key** → 引导用户填 key 或选预设；填完后继续走 API，不切规则。
2. **请求失败（超时/限流/模型报错）** → 明确报错 + [重试] + [换预设/换模型]。
3. **视觉模型不可用** → 提示换视觉模型，或 OCR 降级为文本模型（明确标注识别方式）。

## 6. 记忆层 · 使用偏好（本次交付范围，定位 P1）

记忆范围扩充为**四类**，全部本地存储：

| 类别 | 记住什么 | 写入方式 |
|---|---|---|
| **模型偏好** | 常用预设/模型、base_url、api_key | 用户显式设置即保存 |
| **语言偏好** | 界面语言、生成内容语言（中/英） | 用户显式设置即保存 |
| **界面偏好** | 窗口大小/位置、主题（深/浅色）、托盘常驻开关 | 用户显式设置即保存 |
| **常用维度与措辞** | 采纳过的维度、自定义措辞习惯 | **AI 提议 + 用户采纳才写入** |

- **怎么落地**：**本地存储**（SQLite 或本地 JSON/配置文件），数据不出本机，隐私优先。
- **写入原则**：**无自动采集、无后台回传**；内容性偏好（维度/措辞）严格"AI 提议、用户采纳才写入"；设置类偏好（模型/语言/界面）由用户显式操作直接保存，不涉及 AI 提议。
- **生效方式**：下次启动/生成时自动应用——模型偏好决定默认模型、语言偏好决定界面与输出语言、界面偏好还原窗口与主题、维度/措辞习惯作为上下文注入模型，让其优先产出符合用户习惯的条目。
- **边界**：记忆只做"加分项"，不阻塞主流程；无记忆时照样能用。

## 7. 技术形态约束（供架构师参考）

> 本次从"宿主 UI 扩展"改为**独立桌面应用**，架构师需调研确认以下技术点：

1. **桌面框架选型**：Electron vs Tauri（体积/内存/跨平台/开发效率权衡，倾向 Tauri 若以轻量优先，Electron 若以生态成熟优先）。
2. **跨平台**：Windows / macOS / Linux 的取舍（影响打包与截图/剪贴板能力差异）。
3. **多模态模型接入**：OpenAI 兼容协议的视觉输入（图片以 base64 或 URL 传入 message 的 `image_url` 字段），不同厂商视觉模型字段差异需适配。
4. **截图/剪贴板图片能力**：内置屏幕截图工具（首版）、读取系统剪贴板中的图片、拖拽文件读取（不同桌面框架/系统的实现路径不同）。
5. **本地存储方案**：记忆层（四类偏好）+ 配置的本地存储（SQLite / 配置文件），跨平台路径处理。
6. **网络请求与脱敏**：调用用户自填 key 的 API 时，key 只存本地、不写日志、不硬编码。
7. **长对话文本处理**：多轮对话记录可能很长，需处理上下文长度（截断 / 分段总结 / 压缩），以及拖入文本文件的读取与格式解析（.txt/.md）。

**架构师动手前需先给出**：桌面框架选型结论 + 多模态/OCR 选型结论 + 截图/剪贴板实现路径 + 本地存储选型 + 长文本处理策略，作为技术方案基线。
